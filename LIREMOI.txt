AfriControl — poste
Inspection du 1er octobre 2026

Corrigé dans cette livraison
- La couche nuit et tout agrandissement ne sont plus dessinés en gros carreaux. La tuile native reste nette. Si on agrandit, l'image est lissée.
- La vue proche (Ident) demande la mosaïque à 0,3 m là où la tuile existe. Sinon le niveau réel en dessous, pas une grille de couleurs.
- Le 1090ES interroge adsb.fi puis adsb.lol, une cellule après l'autre, pour ne plus perdre le flux sur un refus 429.
- Une piste 1090ES verrouillée est croisée avec le METAR le plus proche, le SIGMET qui la couvre, et le GNSS (NIC du bord, cellule au sol).

Constat, pas un défaut du poste
- À l'heure des captures, FTTJ, Niamey et Accra n'avaient aucun squitter. Le même flux en avait 31 au-dessus de Paris. Le METAR FTTJ affiché était bien le message réel.
- La photo de route avec un véhicule est la mosaïque publique fine. Ce n'est pas une prise de la dernière heure. La photo de l'heure reste Meteosat, environ 1 km, sur les vues larges.

Installation
- Node 22. Dans ce dossier : npm install, puis npm run dev.
- Le poste écoute sur le port 8080.
- Poste isolé / hors ligne : l'authentification est COUPÉE par défaut (fichier .grok/app-env.json,
  VITE_AUTH_ENABLED=false) — le poste ouvre DIRECTEMENT la console, sans login ni base de données.
  C'est le bon mode pour un site isolé où l'accès physique au poste est déjà contrôlé.
  Si le poste reste bloqué sur « Chargement du poste… », c'est que l'auth s'est activée sans
  serveur d'auth derrière : vérifier que .grok/app-env.json existe, ou lancer
  VITE_AUTH_ENABLED=false npm run dev (Windows : $env:VITE_AUTH_ENABLED="false"; npm run dev).
- Pour ACTIVER un login multi-agents : mettre VITE_AUTH_ENABLED=true ET fournir une base
  (DATABASE_URL) ; sinon l'auth n'a pas de serveur et le poste reste sur l'écran de chargement.

Lancer comme un vrai serveur (sans mode dev)
- npm run dev est pratique mais c'est le mode développement. Pour un serveur autonome lançable
  avec node, builder avec le preset node-server :
    NITRO_PRESET=node-server npm run build
  → produit .output/server/index.mjs. Le lancer :
    PORT=8080 node .output/server/index.mjs
  Flux externes (1090ES, météo) derrière un proxy : ajouter NODE_USE_ENV_PROXY=1 et HTTPS_PROXY.
- Par défaut le build vise Vercel ; NITRO_PRESET choisit la cible, rien d'autre à changer.
- Persistance (journal, personnel, preuves) : fournir une base Postgres via DATABASE_URL. Sans
  base, le cœur live (1090ES, carte, météo, phonie) fonctionne, mais rien n'est conservé au redémarrage.

Intégrer ta propre API
- Un point d'entrée HTTP interne : créer src/routes/api/<nom>.ts sur le modèle de src/routes/api/tile.ts
  — createFileRoute("/api/<nom>") avec server.handlers.GET/POST. Accessible sur /api/<nom>.
- Appeler TON API externe depuis le serveur (la clé reste côté serveur, jamais exposée au navigateur) :
  créer un module <nom>.server.ts qui fait le fetch, et l'exposer via createServerFn (voir
  src/lib/vigilair/live-feeds.ts). Le composant appelle la fonction, le navigateur ne voit que le résultat.

Assistant IA DeepSeek (ta clé) — Capteurs > Outils
- Le poste intègre un assistant qui raisonne sur l'image live réelle (1090ES, METAR, SIGMET, Kp).
  Il répond en français, bref, sans inventer de pistes. Réception seule : il ne commande rien.
- Ta clé DeepSeek est un SECRET : elle vit UNIQUEMENT dans la variable d'environnement du serveur
  AFRICONTROL_DEEPSEEK, posée AU LANCEMENT. Jamais dans le code, le zip livré, Git, ni .grok/app-env.json
  (ce n'est PAS une variable VITE_ : celles-là partent dans le navigateur). La clé ne quitte jamais le
  serveur ; le navigateur ne reçoit que la réponse texte.
    AFRICONTROL_DEEPSEEK=sk-xxxx PORT=8080 node .output/server/index.mjs     (serveur autonome)
    AFRICONTROL_DEEPSEEK=sk-xxxx npm run dev                                 (dev)
    Windows PowerShell :  $env:AFRICONTROL_DEEPSEEK="sk-xxxx"; npm run dev
- Capteurs > Outils > « Assistant IA du poste » : bouton « Tester la clé » (vérifie que l'API répond)
  et un champ question libre. Le même bouton sert au « Briefing situation » (DeepSeek si la clé est posée).
- IMPORTANT : si une clé a été exposée (collée dans un message, un ticket, une capture), la RÉVOQUER et en
  régénérer une sur platform.deepseek.com. Une clé ne se partage pas en clair ; seul le serveur la détient.

Antenne 1090 du poste (clé SDR + dump1090)
Lancer dump1090 avec le port brut AVR, et un port web qui ne prend pas 8080 (celui de AfriControl) :
  dump1090 --interactive --net --net-ro-port 30002 --net-http-port 8090 --aggressive
AfriControl s'y branche seul sur 127.0.0.1:30002 et décode chaque trame (Capteurs > Antenne).
Récepteur sur une autre machine :  AFRICONTROL_1090=192.168.1.50:30002 npm run dev
  (Windows PowerShell :  $env:AFRICONTROL_1090="192.168.1.50:30002"; npm run dev)
Position de l'antenne :  AFRICONTROL_ANTENNE=12.1331,15.0339   Couper la liaison :  AFRICONTROL_1090=off
Réception seule : AfriControl décode l'ADS-B / Mode S entendu en clair, il n'interroge ni n'émet.
Les anciens noms VIGILAIR_1090 / VIGILAIR_ANTENNE sont encore lus : un poste déjà réglé n'a rien à changer.

GPS du poste (position + heure réelles) — Capteurs > GNSS
- Branche un RÉCEPTEUR GPS (clé USB GPS, module u-blox, ou un terminal qui sort du NMEA). L'antenne
  GPS seule ne suffit pas : une antenne sort du signal RF, pas des données — il faut le récepteur.
- Le poste lit le NMEA et en tire la position et l'heure UTC réelles ; un fix sert aussi de position
  d'antenne au décodage 1090 (prioritaire sur AFRICONTROL_ANTENNE). Lecture seule, rien n'est émis.
    AFRICONTROL_GPS=/dev/ttyUSB0 npm run dev        clé USB / série (Linux/macOS ; baud AFRICONTROL_GPS_BAUD, défaut 9600)
    AFRICONTROL_GPS=127.0.0.1:2947 npm run dev      flux NMEA en TCP (gpsd « gpspipe -r », ser2net, device réseau)
    AFRICONTROL_GPS=off                             coupe la liaison (défaut : non réglée)
- Windows : expose la clé USB GPS en TCP (gpsd, ser2net, com2tcp) puis AFRICONTROL_GPS=hote:port.
- Capteurs > GNSS montre le fix (position, UTC, satellites, HDOP) ; le diagnostic (Outils) l'affiche aussi.

Imagerie satellite de nuit — honnêtement
- « Visible » est de la lumière solaire réfléchie : de nuit, c'est NOIR (physique, pas un bug).
- Pour les nuages la nuit : « IR 10.5 » (infrarouge, 24 h/24) ou « Nuit » (bande jour/nuit VIIRS :
  nuages au clair de lune + lumières des villes). La capture nocturne avec villes = cette couche-là.
- « Visible » n'est noir la nuit QUE sur les vues LARGES (AES/Sahel/Monde), où il vient du
  géostationnaire. En DÉTAIL (1,2 m / 0,3 m / Veille / Approche), « Visible » est l'ARCHIVE Esri
  World Imagery : une mosaïque NETTE, valable jour comme nuit. On lit les rues la nuit aussi.
- Bascule AUTO jour/nuit (bouton sous les couches, actif par défaut) : la nuit, SEULES les vues
  larges passent en « Nuit » (le détail garde l'archive nette) ; retour « Visible » au jour ou dès
  qu'on repasse en détail. Un choix manuel (IR, Nuit…) n'est jamais écrasé ; « Auto nuit coupé »
  laisse la main. Le bouton affiche « Auto · Nuit » seulement quand il a réellement basculé.
- Imagerie qui semble floue/sombre alors qu'on est EN LIGNE : laisser 10–20 s au premier affichage
  d'une zone (l'imagerie fine Esri 0,3 m charge progressivement, tuile par tuile). Tant qu'elle
  n'est pas arrivée, le poste montre la mosaïque locale plus grossière (37 m) si elle est installée,
  sinon du sombre. En ligne, l'imagerie fine finit toujours par remplacer la locale.

Couverture imagerie par continent — quelle couche pour voir le monde
- Pour une vue qui couvre Afrique + Moyen-Orient + Europe + Russie + Asie en continu : utiliser la
  couche « IR 10.5 » (infrarouge). Mesuré : l'IR rend une imagerie riche partout, 24 h/24 (y compris
  Asie et Russie Est). La couche « Nuit » (VIIRS) couvre aussi le monde la nuit (lumières des villes).
- AUTO : le bouton « Auto IR monde » (sous les couches, actif par défaut) bascule tout seul sur IR
  dès qu'on passe aux vues larges (AES / Sahel / Monde) → couverture monde garantie, jour et nuit ;
  retour « Visible » en détail (archive nette). Priorité : IR (vue large) > Visible (détail). Un choix
  manuel de couche n'est jamais écrasé. « Auto IR coupé » laisse « Auto jour/nuit » gérer la nuit.

Actualisation de l'imagerie — à quelle cadence (honnêtement)
- Vue continent / monde (IR ou Visible géostationnaire, Meteosat/GOES/Himawari) : ~10 minutes (le
  satellite rebalaie le disque toutes les ~10 min). C'est le quasi temps réel pour nuages / météo.
- Couche « Nuit » (VIIRS DNB, satellite polaire) : ~1 à 2 passages par jour → quotidien, pas continu.
- Détail « Visible » (Esri World Imagery 0,3 m) : c'est une ARCHIVE, pas du live — des mois à des
  années selon la zone. Le crédit en bas de carte le dit (« archive, pas une prise du jour »).
- Sentinel-2 (couche S2) : revisite ~5 jours, composite « moins nuageux » ≤ 20 jours.
- Feux FIRMS (VIIRS thermique) : quelques heures à quotidien. METAR/SIGMET : à chaque relevé (~20 s
  côté poste, sur des bulletins publiés toutes les ~30–60 min). 1090ES réseau : ~toutes les 20 s.
- « Visible » est plus limité : c'est le disque géostationnaire METEOSAT (Afrique, Moyen-Orient,
  Europe, Russie Ouest) ET seulement de JOUR (lumière solaire réfléchie). L'Asie / l'Extrême-Orient
  ne sont pas sur Meteosat, et la moitié du globe en nuit est toujours noire sur Visible — c'est la
  physique du géostationnaire, pas un bug. « Rien de vue » en vue large = on est sur Visible, de nuit
  ou sur l'Asie. Passer sur « IR 10.5 » pour la couverture monde continue.

Imagerie en haut zoom sur un SITE ISOLÉ — la vérité
- L'imagerie gratuite (Esri World Imagery) n'a PAS le 0,3 m partout. Sur une grande ville (ex. FTTJ)
  elle va jusqu'au 0,3 m ; sur un site isolé du Sahel, le plus fin existant est souvent ~2–5 m (zoom
  16–17). Au-delà, la tuile n'existe pas (404). Ce n'est pas un bug du poste, c'est la couverture.
- Le poste affiche désormais la MEILLEURE imagerie réellement disponible (le zoom le plus fin qui
  existe, agrandi) au lieu d'un carré vide, et le GSD affiché dit la VRAIE résolution (ex. « GSD 2.4 m »
  à la place d'un faux « 0,3 m »). Honnête : on ne maquille pas du 2 m en 0,3 m.
- « Détection » (bandeau voiture/pirogue/homme) N'EST PAS une détection d'objets : c'est un indicateur
  de RÉSOLUTION. À partir du GSD réel, il dit ce que l'image PEUT séparer (voiture, pirogue…) et ce
  qu'elle ne peut pas (« pas une plaque, pas un nom »). Sur un site à 2–5 m, il dira honnêtement qu'on
  ne distingue ni un homme ni un véhicule fin. Pour du vrai sous-métrique sur ton site, il faut une clé
  commerciale taskée (Maxar/Planet) — le poste ne fabrique jamais un faux « live » ni une fausse détection.
- Chaque couche crédite sa vraie source et son vrai âge ; rien n'est simulé.

Verrou auto sur piste réelle
- Sans choix de l'opérateur, le panneau de droite suit la piste 1090ES réelle prioritaire :
  urgence (7500/7600/7700) > drone B6 > militaire > GNSS douteux (NIC < 5) > plus proche de FTTJ.
  Urgence et B6 comptent sur le Tchad, le Darfour et l'AES ; militaire et GNSS sur Tchad et Darfour.
- Le bandeau « VERROU AUTO » dit pourquoi. Un clic sur une piste reprend la main ; « Rendre au
  verrou auto » la lui redonne ; « Couper le verrou auto » laisse le panneau vide.
- Un inject ou un rejeu n'est jamais pris par le verrou auto. La carte ne bouge pas toute seule.

Inject « Rejeu réel »
- Injecter > Rejeu réel : rejoue de VRAIS avions reçus, pas un scénario. Bande de ce poste (les
  30 dernières minutes de veille) ou, au démarrage, l'archive réelle livrée (12 min enregistrées
  le 4 octobre 2026 sur 15 cellules africaines). Entre deux relevés, la position est interpolée.
- Chaque piste porte « REJ » et son heure d'origine ; le bandeau dit d'où vient la bande. ×1 ou ×4.
- Un rejeu ne compte jamais comme live, ne déclenche pas d'intrusion de zone et n'est pas
  croisé avec la météo du jour. Nouvelle archive : node scripts/rejeu-enregistrer.mjs 12 30

Symbologie APP-6 et radar
- Les pistes portent le cadre OTAN APP-6 (le cadre = l'affiliation ; ouvert en bas = aérien).
  Inconnu est l'état par défaut : sans IFF ami ni mandat levé, une piste reste inconnue.
- PPI : portées jusqu'à 20 000 km, vecteur vitesse, nord vrai/magnétique, bascule symboles APP-6 /
  formes plateforme. Fiche « interception » : toutes les données reçues. À 8000 km « couverture
  Afrique », à 12 000+ « couverture monde · tous continents ».
- COUVERTURE CONTINENTALE (pas seulement FTTJ) : le COP est physiquement à N'Djamena, mais l'AO a un
  rayon de ~4200 km (côté 8400 km) et le 1090ES balaie un maillage de cellules sur TOUT le continent —
  Maghreb, Égypte, Sahel/Ouest (Dakar, Bamako, Abidjan, Accra, Lagos), Centre (Yaoundé, Kinshasa,
  Luanda), Corne/Est (Addis, Nairobi, Dar es Salaam) et Australe (Johannesburg, Durban, Le Cap) — plus
  des ancres mondiales. Par courtoisie API, 3 cellules par relevé en rotation ; le CHEF DE DIVISION
  active le « balayage total » (toutes à chaque relevé) pour la photo continentale la plus complète.
  Là où un agrégateur a un récepteur, de vrais avions remontent ; ailleurs la cellule est prête pour
  le jour où un récepteur apparaît. Réception passive, jamais d'identité.
- PISTE MÉMOIRE (transpondeur muet) : quand une piste cesse d'émettre, elle n'est plus laissée FIGÉE
  à sa dernière position en se faisant passer pour un retour vivant — à 800 km/h, un symbole gelé
  45 s est 10 km à côté, et rien ne le disait. Le poste fait maintenant ce que fait un radar : il la
  tient en mémoire, EXTRAPOLE sa position à l'estime (dernier cap, dernière vitesse), fait grandir un
  cercle d'incertitude en pointillé autour du point prédit, écrit « MÉM » avec le nombre de secondes
  de silence, et l'abandonne au-delà de 45 s. Intérêt direct pour la sûreté d'un site : un aéronef
  qui COUPE son transpondeur en approche ne disparaît plus discrètement du scope — il devient une
  piste mémoire signalée, avec une zone d'incertitude qui dit où il peut être.
- RELEVÉ DOUTEUX (trame invraisemblable) : toute position reçue était acceptée telle quelle, si bien
  qu'une trame brouillée, mal décodée ou falsifiée pouvait téléporter une piste. Chaque nouveau
  relevé est désormais confronté au précédent : si le déplacement exigerait une vitesse impossible
  (> 1500 km/h) ou une variation d'altitude impossible (> 80 m/s), le saut est REFUSÉ — la piste
  continue à l'estime et le relevé est signalé avec son motif. Contrôle de cohérence physique du
  signal, jamais une identité : on ne dit pas qui ment, on dit que la trame ne tient pas debout.
  Les deux compteurs (« Pistes mémoire », « Relevés douteux ») sont dans le bandeau de la vue Radar,
  pour que l'opérateur sache en permanence ce qui est MESURÉ et ce qui ne l'est pas.
- APPROCHE D'UN SITE PROTÉGÉ : l'alerte existait mais ne pouvait PAS partir sur du trafic réel — le
  CPA n'était calculé que par la simulation, et une piste 1090ES naissait avec le verrou « déjà
  prévenu » fermé. Autrement dit l'alerte la plus utile d'un poste de surveillance de site ne
  fonctionnait que sur des pistes fictives. Le CPA est désormais calculé sur les pistes réelles, le
  verrou est préservé d'un relevé à l'autre (sinon l'alerte se rejouerait en boucle), et surtout un
  PLAFOND D'ALTITUDE a été ajouté : le CPA est purement horizontal, donc sans ce garde-fou un avion
  de ligne à 10 000 m passant à la verticale d'une mine affichait une distance nulle « en
  rapprochement » et aurait alerté à chaque survol. Ne compte comme approche que ce qui est BAS
  (≤ 1500 m), EN MOUVEMENT, PROCHE (≤ 3,2 km) et EN RAPPROCHEMENT — ce qui laisse passer le cas qui
  compte pour un site isolé : le petit, le lent et le très bas. Géométrie et cinématique, jamais
  d'identité.
- TRANSPONDEUR COUPÉ PRÈS D'UN SITE : la piste mémoire était dessinée mais ne prévenait personne.
  Un aéronef BAS qui cesse d'émettre à proximité d'un site protégé est précisément ce qu'un poste
  doit voir — c'est le geste de qui ne veut pas être suivi. Alerte ÉLEVÉE, une fois par piste, avec
  la durée du silence, l'altitude, la distance au site et le rayon d'incertitude (« ce n'est plus
  une mesure »). Oubliée dès que la piste ré-émet.
- POURQUOI LE SCOPE EST VIDE AU-DELÀ DE QUELQUES KILOMÈTRES (portée constatée) : un poste qui
  annonce « portée 1200 km » et ne montre rien au-delà de 10 km laissait l'opérateur sans moyen de
  trancher entre trois causes très différentes — le ciel est vide, personne n'écoute, ou le logiciel
  coupe. AfriControl le dit maintenant, chiffres en main, et pour les DEUX sources.
    • ANTENNE LOCALE. L'onglet CAPTEURS › Antenne affiche la PORTÉE CONSTATÉE (la plus lointaine
      position réellement reçue) et la distance médiane — pas la portée réglée, qui ne prouve rien.
      En dessous de 25 km, le poste écrit que le 1090 MHz porte à vue et que la limite vient de
      l'INSTALLATION (antenne à l'intérieur, câble trop long, horizon bouché), pas du logiciel, qui
      n'écarte aucune position en deçà de 800 km. Un échantillon vide ou trop maigre ne conclut
      JAMAIS : « rien reçu » veut dire qu'on ne sait pas, pas que l'antenne est mauvaise.
    • RÉSEAU. Mesuré en réel sur l'URL exacte du poste : HTTP 200 et ZÉRO avion dans un rayon de
      463 km autour de N'Djamena, contre 62 à Tunis et 960 à Paris. Le théâtre n'est pas un trou de
      logiciel, c'est un trou de RÉCEPTEURS : les agrégateurs n'ont quasiment personne au Tchad, et
      seule une antenne locale y donne de vrais avions. Le bandeau de source le formule désormais
      ainsi, et surtout il SÉPARE « j'ai regardé, il n'y a personne » de « on m'a refusé la requête »
      (HTTP 429) et de « la liaison a échoué ». Les confondre déguisait une panne de capteur en
      calme plat — un scope vide y ressemblait trait pour trait à un ciel calme.
- RECALAGE D'ÂGE DES POSITIONS (la plus grosse marge d'erreur du radar) : un agrégateur réseau
  livre des positions DÉJÀ VIEILLES — il indique leur âge dans chaque relevé (champ « seen ») — et
  AfriControl prenait l'heure de RÉCEPTION pour l'heure d'OBSERVATION. Autrement dit le poste
  dessinait « vu à l'instant » une position qui pouvait avoir une minute. Mesuré sur 881 avions
  réels : l'âge est de 0,1 s en médiane (l'agrégateur est bon), mais 6,7 % des positions dépassent
  5 s, 3,1 % dépassent 30 s, et la pire était à 2,65 km de là où le symbole était peint. La moyenne
  rassurait, la QUEUE mentait. Désormais chaque relevé garde sa MESURE BRUTE avec son heure réelle
  d'observation, et le scope affiche le meilleur ESTIMÉ pour MAINTENANT (la piste est avancée à
  l'estime de son propre âge) ; au-delà de 5 s d'âge, le symbole le dit (« MÉM »), parce que
  l'opérateur a le droit de savoir que ce point est prédit et non mesuré. Trois conséquences :
    • une piste déjà en retard à la réception est tenue en mémoire DÈS son premier relevé — un
      transpondeur coupé ne peut plus se cacher derrière « l'agrégateur me liste encore » ;
    • la plausibilité compare enfin les positions MESURÉES sur leur VRAI intervalle d'observation.
      Elle comparait des mesures distantes de 40 s sur un intervalle de réception de 10 s, et lisait
      2876 km/h là où l'avion en tenait 719 : du BON trafic était refusé comme « saut de position ».
      Vérifié chiffre en main, c'est le faux positif que ce lot supprime ;
    • l'extrapolation repart de la MESURE, jamais de la position déjà affichée — sinon l'âge était
      compté deux fois et le symbole s'éjectait un peu plus loin à chaque tour.
  AFFICHER N'EST PAS PRÉVENIR : le scope signale dès 5 s, l'alerte « transpondeur muet près d'un
  site » n'ouvre la bouche qu'au-delà de 30 s de silence franc. Sans ce second seuil, la latence
  ordinaire de l'agrégateur (7 % des relevés) aurait noyé le poste sous des alertes de sûreté.
- CE QUE L'AÉRONEF DÉCLARE DE SA PROPRE PRÉCISION : un aéronef coopératif ne dit pas seulement OÙ
  il est, il dit AVEC QUELLE PRÉCISION il le sait (NIC, DO-260B), ce qui se traduit par un RAYON DE
  CONFINEMENT — et l'agrégateur relaie même ce rayon tout cuit. AfriControl jetait cette information
  et peignait toutes les pistes comme des points exacts. Mesuré sur 881 avions réels : 14 % déclarent
  un rayon supérieur à 185 m, et deux d'entre eux 7,4 km. Un point exact à 7 km près, sur un scope de
  sûreté, c'est un mensonge par omission. Le scope trace désormais un cercle d'incertitude À
  L'ÉCHELLE, en composant en quadrature les DEUX causes indépendantes : ce que l'aéronef admet
  ignorer, et ce que notre extrapolation ajoute quand il s'est tu. Vérifié de bout en bout par la
  voie antenne (vraies trames DF17) : NIC 8 (185 m) → rien de tracé, car à 50 km de portée ce serait
  un pixel et gonfler le cercle mentirait dans l'autre sens ; NIC 4 → cercle + « ±3.7 km » ; NIC 2 →
  grand cercle + « ±14.8 km ». Sur le lot réel, 872 pistes sur 881 portent enfin une incertitude
  (médiane ±186 m), et seules 92 dépassent 1 km — donc le scope reste lisible.
- FAUSSE CARTE DE BROUILLAGE GNSS (corrigé) : le poste signalait des zones de brouillage qui
  n'existaient pas. Le NIC est une propriété de la position ÉMISE par l'aéronef ; or une piste MLAT
  n'émet AUCUNE position — elle est localisée par multilatération depuis le réseau de récepteurs, et
  n'a donc pas de NIC à dégrader. En comptant son NIC absent comme « GNSS dégradé », AfriControl
  affichait 9 cellules de « brouillage élevé » sur un relevé réel là où il n'y en avait aucune :
  8 artefacts purs (89 pistes MLAT), plus une cellule tirée de 3 avions. Deux correctifs : seules
  les pistes qui émettent réellement une position sont interrogées, et une cellule doit compter un
  minimum d'aéronefs pour qu'un pourcentage veuille dire quelque chose (7 cellules sur 28 du lot
  réel en comptaient moins de 10 — « 1 sur 2 » s'affichait « 50 % »). Résultat vérifié sur le même
  lot : 9 cellules « élevé » → 0, le maximum restant étant 7 % sur un échantillon de 46 avions.
  Le bandeau Radar compte désormais les « Positions calculées » (10 % du trafic réel), pour qu'elles
  ne soient jamais confondues ni avec une mesure exacte, ni avec un brouillage.
  Piège retenu au passage : « rc = 0 » de l'agrégateur signifie INCONNU, pas « rayon nul ». Les 102
  pistes concernées sont les PIRES du lot ; le lire au pied de la lettre les aurait fait passer pour
  les meilleures.
- ALTITUDE RECALÉE DE L'ÂGE : l'altitude vieillit comme la position. L'enjeu est modeste (2 pistes
  sur 881 fausses de plus de 150 m, la pire de 370 m) mais le plafond d'alerte site est à 1500 m,
  donc une descente compte. Le taux de montée est BORNÉ avant d'être appliqué : certains relevés
  réels annoncent +33 245 ft/min (169 m/s), et les appliquer tels quels AJOUTERAIT de l'erreur au
  lieu d'en retirer.
- ADRESSE ICAO PARTAGÉE (doublon) : deux émetteurs sur la même adresse ne se voient PAS par un
  dédoublonnage par adresse — celui-ci garde simplement le dernier reçu. Ce qui les trahit, c'est
  que leurs positions alternent : un relevé sur deux est physiquement impossible. Compter les refus
  CONSÉCUTIFS ne marcherait pas (une bonne trame sur deux remettrait le compteur à zéro) : on compte
  donc les relevés incohérents d'un même ÉPISODE, qui se referme 60 s après le dernier incident.
  Au-delà de 3, le poste ne parle plus de « trame ratée » mais d'adresse vraisemblablement tenue par
  deux émetteurs. Un relevé douteux isolé reste signalé pour ce qu'il est. Incohérence de signal,
  jamais une identité : on ne dit pas qui ment, on dit que l'adresse ne tient pas debout.
- Débruitage (touche D, ou « Pertinent » dans Peinture) : à large portée le scope se remplit de
  transit civil lointain. Le débruitage ne garde que ce qui compte pour la sûreté du site — urgence,
  militaire, GNSS dégradé (NIC < 5), et tout contact à moins de 300 km de FTTJ — plus la piste
  verrouillée. Exemple mesuré : 128 contacts à 20 000 km → 3 pertinents. La liste et le compteur
  se rafraîchissent aussitôt. Le reste n'est pas supprimé, juste masqué tant que le débruitage est actif.
- Le « clutter » cosmétique du scope (neige radar) est bas par défaut (6 %), réglable dans Peinture.
- Fond de carte : là où l'imagerie géostationnaire n'existe pas (zoom monde/continent, pôles), le
  poste sert une tuile vide propre au lieu d'erreurs 404 qui polluaient la console — rien à régler.

Balayage continental (chef de division) — Capteurs > 1090ES
- Par défaut le poste interroge 3 cellules du continent par relevé (courtoisie envers les API
  publiques). Le chef active le balayage total : toutes les cellules Afrique + ancres mondiales
  (Europe, Amériques, Asie, Océanie) à chaque relevé — le radar « tous continents » montre alors
  de VRAIS contacts 1090ES, pas une carte vide. Les cellules partent en lots parallèles bornés.
- Toute piste réelle est verrouillable : un clic sur l'indicatif dans la liste 1090ES l'ouvre.

Diagnostic du poste — Capteurs > Outils
- Une vue qui dit honnêtement l'état de CHAQUE source : 1090ES réseau, METAR, SIGMET, météo spatiale,
  antenne 1090 locale, phonie ATC, clé assistant DeepSeek, clé imagerie Sentinel. Vert = répond,
  jaune = réglé mais rien reçu / vieux, rouge = réglé mais en échec, gris = non réglé (optionnel).
- Il n'interroge PAS les API (aucun martèlement) : il lit le dernier relevé en cache, l'état mémoire
  de l'antenne et de la phonie, et la présence des clés. « 0 contact » est un vrai constat là où le
  réseau public n'a pas de récepteur, jamais une panne déguisée. Bouton « Rafraîchir ».
- Chaque ligne en défaut porte un bouton d'action direct : « Régler l'antenne » (onglet Antenne),
  « Ouvrir Phonie ATC », « Configurer la clé » (DeepSeek / Sentinel). On va au bon réglage en un clic.

Compte rendu de quart (DeepSeek) — Journal de preuve
- En tête du Journal : bouton « Rédiger le compte rendu ». DeepSeek rédige un AAR structuré (période,
  volume, faits marquants, points d'attention, recommandation pour la relève) à partir des SEULS
  bulletins versés. Les injects sont marqués EXERCICE et ne sont jamais comptés comme trafic réel.
- La clé reste au serveur (AFRICONTROL_DEEPSEEK). Le compte rendu est une aide à relire et valider,
  pas une pièce scellée : les bulletins hashés restent la preuve.

Enregistrements archivés — Capteurs > Outils
- Copie de ce que le poste a réellement entendu (veille 30 min), écrite sur disque dans recordings/.
  Archivage auto toutes les 15 min dès 3 min de veille (activable/désactivable par le chef), plus
  « Archiver maintenant ». Téléchargeable en JSON (format du rejeu réel).

Phonie ATC — réception seule (Capteurs > Phonie ATC)
- Enregistre le flux audio de TON propre récepteur (clé SDR + rtl_airband/rtl_fm, bande aéro VHF
  publique) : AFRICONTROL_ATC=http://127.0.0.1:8000/atc.mp3 npm run dev
- Réception seule : le poste lit un flux public et l'archive, sans limite (segments de 10 min),
  activable/désactivable. Il n'accorde aucune radio, ne décode pas la parole, n'émet jamais.
  Segments téléchargeables. Pas d'écoute d'autre chose que l'aéronautique en clair.

Alertes feu (FIRMS) — ce que le capteur peut, honnêtement
- Détection thermique VIIRS : foyers groupés, puissance FRP (MW), confiance, jour/nuit, ville la
  plus proche. Seuil abaissé au théâtre élargi (Tchad, Darfour, AES).
- Limite physique : le pixel VIIRS fait 375 m. On repère un FOYER, pas l'image d'une voiture.
  Voir une voiture qui brûle demande du sous-métrique (30 cm) commercial et taské (Maxar, Planet) —
  pas un flux public rafraîchi toutes les 30 min. Sans clé d'un fournisseur commercial, le poste
  n'affiche pas un faux « live » : le crédit en carte dit toujours la vraie source et le vrai âge.

Phénomènes mondiaux — le lointain à un clic, sans noyer le poste
- Les crues, cyclones, séismes, volcans et feux du MONDE ENTIER sont captés en temps réel (GDACS,
  EONET, USGS, FIRMS) et restent sur la carte et dans les graphiques SANS sonner. Un phénomène
  lointain (Indonésie, Népal…) ne doit pas noyer la veille de FTTJ : il n'arme pas d'alerte.
- Pour les retrouver quand même, le bandeau d'alertes porte une pastille « N monde » (icône globe).
  Un clic ouvre le volet « Phénomènes mondiaux » : TOUS les événements réels, triés par gravité puis
  distance, chacun avec « Capture imagerie » (imagerie réelle de la zone — Sentinel-2 10 m si clé,
  sinon IR/Esri). Réception seule : le poste regarde, il ne commande rien.
- SITES MINIERS : une crue, un feu ou un séisme à ≤ 200 km d'un site minier (Komé, Essakane, Tasiast,
  Geita, Kibali…) SONNE toujours en alerte, où qu'il soit sur le continent, même hors du théâtre de
  FTTJ — l'alerte porte « près de <site> (<km>) ». La sûreté d'un site isolé prime ; seuls les feux
  FIRMS lointains de masse restent filtrés pour ne pas saturer.

Imagerie Sentinel-2 fraîche (Copernicus) — Capteurs > Outils, couche « Sentinel-2 »
- Le poste ne possède pas de satellite. Il interroge l'API Copernicus avec le compte GRATUIT de
  l'opérateur (Copernicus Data Space Ecosystem) : images Sentinel-2 fraîches, 10 m natif. On lit une
  piste, un bâtiment, un convoi — pas une voiture isolée. Composite « moins nuageux » ≤ 20 jours,
  crédité honnêtement (fenêtre réelle, jamais un faux « live »).
- Clé gratuite : compte sur dataspace.copernicus.eu, client OAuth, puis
  AFRICONTROL_SENTINEL_ID=<id> AFRICONTROL_SENTINEL_SECRET=<secret> npm run dev
- « Tester la clé » dans Outils vérifie que le jeton est obtenu. Lecture seule : le poste lit des
  images publiques, il ne commande aucun satellite. Pour le sous-métrique (30 cm), il faut une clé
  commerciale (Planet/Maxar) — je ne simule pas ce que le compte gratuit ne donne pas.
- REPLI HORS LIGNE : la mosaïque embarquée dans le poste (public/sentinel) prend le relais quand il
  n'y a pas de clé, pas de réseau, ou que Copernicus refuse — le cas du poste isolé au bout de
  l'antenne. Elle est créditée comme telle (« mosaïque embarquée (hors ligne) »), jamais présentée
  comme une image fraîche, et une tuile absente du disque reste une absence franche, pas une image
  inventée.

Détection auto pour les sites (Capteurs > Changement > Sites surveillés)
- CHANGEMENT AUTO : interrupteur « Surveillance changement auto (Sentinel-2) ». Le poste passe en
  revue les sites (un toutes les 3 min), compare seul les deux passages, et SONNE si la zone a bougé
  au-delà du seuil réglable (% du cadre). C'est de la détection de CHANGEMENT (piste/bâtiment/engin
  neuf), PAS d'objet ni d'identité. Nécessite la clé Copernicus (sinon le scan ne renvoie rien).
- PAR SITE : à l'ajout, « Intrusion aérienne armée » (on/off) et « Rayon alerte phénomènes (km) »
  propre au site (sinon défaut : feu 40 km, crue/séisme 200 km). Les badges « désarmé » / « alerte
  N km » le rappellent dans la liste.
- CAPTEURS SOL (périmètre) : registre partagé (caméra / barrière / radar) — l'ENTRÉE pour la
  détection temps réel véhicule/personne AU SOL, ce que l'imagerie satellite ne fait pas. États
  manuels (ok / alarme / HS) pour l'instant ; une alarme SONNE au bandeau. Un vrai capteur poussera
  son état sur ce registre quand le matériel sera câblé (data/sensors.json, server fns dédiées).
- CE QU'ON NE FAIT PAS : identification / suivi automatique de personnes ou de véhicules SUR L'IMAGE.
  Deux raisons : l'imagerie est archivée (pas du direct, donc pas de suivi temps réel), et c'est du
  ciblage, pas de la sûreté de site. Le temps réel au sol passe par des capteurs sol, pas l'image.

Nos drones ET CAMÉRAS — suivi ami + imagerie comme SOURCE D'ANALYSE (Capteurs > Changement > « Nos drones et caméras »)
- REGISTRE PARTAGÉ MULTI-SOURCES : l'opérateur inscrit ses DRONES et ses CAMÉRAS FIXES de site, chacun
  avec TOUS ses paramètres de liaison : Type (drone/caméra), Nom, Identifiant (hex ICAO/indicatif pour
  un drone ; repère libre pour une caméra), Site, et le FLUX soit par Hôte + Port + Chemin, soit par URL
  directe. L'URL EFFECTIVE est reconstruite depuis hôte:port/chemin (source unique de vérité, aussi
  pour la garde du proxy). Partagé par tout le poste (data/drones.json), hydraté au démarrage/focus.
- JOURNAL DE CONNEXION PAR SOURCE : chaque relevé de la veille est journalisé (OK / ERR + heure + état :
  mouvement %, nb de pistes, ou la raison de l'échec). L'état de liaison « en ligne / injoignable » est
  affiché par source, et le journal se déplie d'un clic — le port et la santé de chaque caméra/drone
  sont ainsi intégrés et visibles dans AfriControl.
- SUIVI AMI : une piste 1090ES (si le drone émet l'ADS-B) dont le hex/indicatif correspond à un drone
  inscrit devient AMI (affiliation « drone ») : elle n'est PLUS comptée comme intrusion dans les
  bulles, et au lieu d'une alerte « UAS B6 » le poste pose une info « notre drone en vol ». Retirer le
  drone du registre lui rend sa pleine évaluation au relevé suivant.
- IMAGERIE = SOURCE D'ANALYSE, PAS UN FOND : si le drone expose une image fixe (station sol / nacelle),
  la « Veille mouvement (imagerie drone) » récupère une trame (proxy serveur, pour lire les pixels),
  la compare à la précédente, et SONNE si une part du cadre a bougé au-delà du seuil réglable (% du
  cadre). C'est de la détection de MOUVEMENT / PRÉSENCE — jamais une identification de personne.
- NATURE DE LA PRÉSENCE (sans identité) : le poste regroupe les pixels qui ont bougé en ZONES connexes
  et lit leur géométrie — nombre de zones, taille, où dans le cadre — pour en tirer un INDICE prudent
  (« silhouette compacte / piéton possible », « masse large / véhicule possible », « indéterminée »).
  C'est une CLASSE, jamais un NOM : un indice à confirmer à l'œil, pas une reconnaissance d'objet.
- DÉTECTION PAR SOUSTRACTION DE FOND MULTI-TRAMES : le poste tient un MODÈLE DE FOND = la MÉDIANE des N
  dernières trames (pas une seule moyenne), et compare la trame courante au fond. Un objet qui traverse
  ne décale pas la médiane, un éclair d'une trame est rejeté → détection plus stable. Chaque objet
  apparaît UNE fois, à sa POSITION COURANTE (une zone pleine) — plus de double bande, et deux cibles
  proches se séparent mieux. Le fond est GELÉ sous les pistes confirmées pour ne jamais absorber un
  objet suivi. Court warmup au démarrage pour remplir la fenêtre.
- PISTAGE MULTI-CIBLES (sans identité) : chaque zone d'avant-plan devient une détection, associée d'une
  trame à l'autre par plus-proche-voisin. PLUSIEURS pistes sont suivies en parallèle, chacune avec son
  id stable (T1, T2…), son SENS de déplacement à l'écran (droite, haut-gauche…) et sa VITESSE estimée ;
  une piste perdue est maintenue (coast) quelques trames avant d'être abandonnée. Sur la capture : une
  trace bleue + un label par piste. C'est le « follow » des drones grand public, version sûreté : on
  suit OÙ VA CHAQUE présence, jamais QUI elle est.
- CAPTURE DE PREUVE POUR L'OPÉRATEUR : à la détection, la trame est FIGÉE avec la zone de mouvement
  surlignée (orange), la plus grande zone encadrée et la trace de suivi ; bouton « Capture » dans la
  liste. L'opérateur OUVRE la capture, REGARDE, et IDENTIFIE à l'œil. C'est lui qui reconnaît qui c'est
  — jamais une IA.
- ALERTE ZONE RENFORCÉE : si le SITE du drone est un périmètre armé (mine, ou site surveillé armé),
  l'alerte passe en CRITIQUE « Présence sur périmètre armé » avec « envoyer une patrouille ». Sinon
  elle reste « Mouvement détecté » (élevée). Bandeau + bip dans les deux cas.
- PRÉSENCE IMMOBILE TENUE INDÉFINIMENT : une piste qui ne bouge plus est étiquetée « immobile Xs »
  (durée d'arrêt) et MAINTENUE sans limite — le fond gelé sous elle l'empêche de se fondre, si bien
  qu'un intrus qui se fige reste suivi (et se re-verrouille au moindre geste). Elle n'est libérée que
  lorsque sa zone redevient VIDE plusieurs trames (l'objet est vraiment parti).
- OCCLUSION / CROISEMENT : quand deux pistes se recouvrent, la piste « perdue » est maintenue (coast)
  le temps du croisement, le poste note « croisement de pistes », ET chaque piste porte une SIGNATURE
  D'APPARENCE non-biométrique (luminance moyenne + taille de la zone). À la séparation, chaque piste
  retrouve SA cible par cette apparence (« le plus clair / le plus grand reste avec le sien »), pas
  seulement par la position — les id se récupèrent même quand les cibles se croisent de près. C'est de
  l'apparence (clair/sombre, grand/petit), JAMAIS une identité (ni visage, ni plaque, ni « qui »).
- PARADE ÉCLAIRAGE : un basculement GLOBAL d'image (exposition, voile, nuage, phare) fait virer une
  énorme part du cadre d'un coup — ce n'est pas une intrusion. Le poste le reconnaît, ré-étalonne vite
  le fond, note « variation d'éclairage » et N'ALERTE PAS.
- SABOTAGE CAMÉRA (l'intrus interne) : la vraie parade contre celui qui TRAVAILLE sur le site et croit
  « passer » en neutralisant la caméra. On ne cherche JAMAIS à reconnaître la personne (pas d'identité) —
  on surveille la SURVEILLANCE elle-même. Le poste mesure en continu la luminance et la stabilité de
  chaque flux et lève une alerte CRITIQUE « SABOTAGE caméra » dans quatre cas :
    · MASQUÉE  — objectif couvert / peint / sac dessus : l'image devient noire ou uniforme (plus aucun
      détail) pendant plusieurs trames d'affilée.
    · FIGÉE    — flux gelé / rejoué en boucle / câble image coupé : les trames restent strictement
      identiques alors qu'une vraie scène bouge toujours un peu.
    · DÉPLACÉE — le coup d'après de celui qui sait qu'un objectif bâché se voit : il TOURNE la caméra
      (vers un mur, le ciel, le sol) ou pose un obstacle devant. L'image reste claire et vivante, donc
      invisible aux deux tests ci-dessus. Le poste compare le MOTIF de la scène à la vue de référence
      qu'il a apprise de cette caméra. Le motif est normalisé avant comparaison, en décalage ET en
      contraste : un nuage ou un phare DÉCALENT la scène, le jour qui tombe la MULTIPLIE (l'éclairement
      module la réflectance) — ni l'un ni l'autre ne compte, seule la géométrie de la vue compte.
      Échelle : 0 = même vue, 2 = motif inversé ; on alerte au-delà de 0,8. Mesuré sur banc : 0,003
      entre deux trames de la même vue, 0,003 sur tout un crépuscule, 2,0 caméra détournée. Plus patient que les autres (un camion qui se gare change aussi le motif) : on
      n'alerte que si ça DURE. La référence suit la dérive légitime (végétation, saisons) mais n'adopte
      JAMAIS d'elle-même une vue sabotée ; si c'est l'opérateur qui a volontairement re-visé la caméra,
      un bouton « Ré-apprendre la vue » valide la nouvelle visée.
    · COUPÉE   — caméra débranchée / hors tension : le flux ne répond plus (déjà remonté par le journal
      et, pour les caméras réseau des sites distants, par la re-scrutation périodique « caméra DOWN »).
  LA VRAIE IMAGE : au moment du sabotage, la trame du moment ne montre plus rien d'exploitable (écran
  noir, bâche, mur). Elle ne vaut RIEN comme preuve. Le poste garde donc en permanence la dernière vue
  NETTE de chaque caméra, et c'est ELLE qu'il présente comme preuve — horodatée « VRAIE IMAGE · hh:mm:ss »,
  zoomable, et embarquée dans le dossier PDF. La trame neutralisée reste affichée à côté en vignette
  « ÉTAT ACTUEL » : elle prouve que la caméra a bien été neutralisée. L'opérateur a donc les deux :
  ce que la caméra voyait juste avant, et ce qu'on lui a fait.
  GARDE-FOU NUIT (la question qui décide de tout sur un poste isolé) : une caméra sans éclairage voit
  noir chaque nuit. Ce qui sépare la nuit d'un objectif bâché, ce n'est pas la noirceur, c'est la
  MANIÈRE d'y arriver : le crépuscule fait perdre quelques points de luminance par trame, une bâche
  fait tomber l'image D'UN COUP. Le poste ne crie donc au « noir » que si l'entrée dans le noir a été
  BRUTALE. Deux conséquences assumées : la nuit ne déclenche rien, et une caméra DÉJÀ dans le noir ne
  peut pas détecter qu'on la bâche (il n'y a plus rien à perdre). Pour la même raison, « image
  uniforme » ne compte que CLAIRE (bâche, peinture) — une image noire uniforme, c'est la nuit.
  Le message dit clairement : la caméra est neutralisée, quelqu'un cherche peut-être à passer sans être
  filmé — vérifier sur place / envoyer une patrouille. Détection de signal, sans identité : ce qui est
  détecté, c'est que la SURVEILLANCE a changé d'état, jamais qui est devant l'objectif.
- FLUX / CADENCE : la cadence est réglable (Normale 15 s · Rapprochée 5 s · Continue 3 s) — plus serré
  = suivi quasi continu. L'URL accepte une IMAGE FIXE (snapshot JPEG) ou un FLUX MJPEG (le proxy en
  extrait la première trame). Le RTSP n'est PAS pris en charge directement (navigateur incapable de le
  lire) : il faut une passerelle qui le transforme en MJPEG / snapshot.
- CAPTURE PLEINE RÉSOLUTION + ZOOM : la capture de preuve n'est plus réduite — elle est dessinée à la
  taille native de la trame (plafonnée à 960 px de côté pour rester légère), en JPEG net, SANS voile
  orange qui masquerait les détails. Un clic sur l'image la passe en grand (zoom) : l'opérateur lit
  LUI-MÊME la scène — la plaque, le visage, l'inscription — à l'œil, sur une image fidèle. Le poste, lui,
  ne lit toujours que du mouvement ; la lecture d'identité est et reste humaine.
- SCAN AUTO (découverte de liaison, gain de temps) : au lieu de chercher à la main le port et le chemin
  d'une caméra, on renseigne l'HÔTE (ex. 10.0.0.9) et on lance « Scan auto ». Le poste teste, côté
  serveur, les ports caméra les plus courants (80, 8080, 8000, 8081…) et, sur ceux qui répondent, les
  chemins snapshot/MJPEG répandus (Axis, Hikvision, Dahua, Foscam, ONVIF, génériques). Dès qu'un port +
  chemin renvoie une IMAGE (ou un flux), il est proposé et « Utiliser » remplit la fiche avec l'URL
  COMPLÈTE (le bon schéma est conservé). Un port RTSP ouvert est signalé (passerelle requise, le
  navigateur ne lit pas le RTSP). C'est de la DÉCOUVERTE DE LIAISON sur VOS propres caméras (quel port
  répond une image), opérateur-initiée, liste de ports/chemins FIGÉE et nombre de sondes plafonné — un
  assistant de câblage, PAS un scanner réseau, et surtout PAS de l'identité : on ne vérifie que « ce
  chemin renvoie-t-il une image ? ».
- CAMÉRA SUR INTERNET (IP publique / DDNS, souvent en HTTPS) : aujourd'hui beaucoup de caméras sont
  joignables PAR INTERNET. On en ajoute une par son hôte public (ex. cam.monsite.ddns.net) ou en
  COLLANT son URL directe (http:// OU https://) ; le « Scan auto » teste aussi le HTTPS (ports 443 /
  8443) et le proxy du flux suit le schéma. NB : une caméra HTTPS doit présenter un certificat VALIDE
  (TLS non désactivé, question de sécurité) ; sinon, passer par http ou une passerelle à certificat
  correct. Ça reste de la liaison vers VOTRE caméra, pas une identité.
- DÉCOUVERTE ONVIF (réseau, sans taper d'IP) : « Découverte ONVIF » envoie une sonde multicast
  WS-Discovery (239.255.255.250:3702) ; les caméras ONVIF du réseau répondent avec l'URL de leur
  service et leurs métadonnées d'ÉQUIPEMENT (nom, modèle, emplacement). Le poste les liste ; « Utiliser »
  remplit l'hôte (type caméra), puis « Scan auto » trouve le chemin du flux. On n'a même plus à connaître
  l'IP. C'est de la découverte d'équipement (« quelles caméras sont là ? »), opérateur-initiée, lecture
  seule, JAMAIS de l'identité de personnes (nom DE LA CAMÉRA, pas de qui que ce soit). Si le réseau ne
  route pas le multicast (certains VLAN/conteneurs) ou la caméra n'est pas ONVIF : la liste revient vide
  sans bloquer — on passe alors au « Scan auto » avec l'IP, ou à l'URL directe.
- SCAN DE PLAGE (LONGUE DISTANCE, de l'antenne à la porte) : le multicast ONVIF s'arrête au segment
  local ; il ne traverse ni routeur ni liaison radio. Pour atteindre les caméras d'un POSTE DISTANT (au
  bout de l'antenne, sous-réseau routé jusqu'ici), « Scan de plage » balaie une PLAGE d'adresses — CIDR
  (10.20.0.0/24), dernier octet (10.20.0.10-40), préfixe (10.20.0.) ou IP seule. Le poste teste la
  présence d'un équipement (connexion TCP sur les ports caméra), trouve le flux sur les hôtes vivants, et
  enrichit le nom par une sonde ONVIF UNICAST (qui, elle, traverse les routeurs). Chaque caméra trouvée a
  déjà son chemin, prête à inscrire. Borné à un /24 (256 hôtes max ; au-delà, on scanne par tranches),
  opérateur-initié : c'est un balayage de VOS réseaux de sites (le /24 que VOUS donnez), PAS un scanner
  d'Internet de masse — une caméra exposée sur Internet s'ajoute, elle, par son adresse propre
  (hôte public / DDNS / URL, cf. ci-dessus). Jamais d'identité.
- ENREGISTREMENT EN LOT + ENCHAÎNEMENT : « Tout inscrire » enregistre d'un coup toutes les caméras
  trouvées (par ONVIF ou par scan de plage) — pour une caméra sans chemin connu, le flux est cherché
  automatiquement. Et « Utiliser » (ONVIF ou plage) enchaîne directement le Scan auto du chemin : un seul
  geste de la découverte à la fiche prête. Toujours type « caméra », sans identité.
- SITES DISTANTS MÉMORISÉS + SECTEURS + RE-SCAN PÉRIODIQUE : on nomme chaque site distant, on le range
  dans un SECTEUR (ex. « Secteur Est ») et on mémorise sa PLAGE réseau (data/sitenets.json, partagé par
  le poste), pour la RE-SCANNER D'UN CLIC. Les sites sont groupés par secteur : « Re-scanner le secteur »
  balaie tout un secteur d'un bouton, « Tout re-scanner » balaie tous les sites. Chaque re-scan compare
  aux caméras vues la fois d'avant et SIGNALE un changement de présence : une caméra TOMBÉE (disparue —
  liaison coupée, panne, sabotage) ou une NOUVELLE apparue sur le périmètre. Un interrupteur « Re-scan
  automatique » (toutes les 5 / 15 / 30 / 60 min) fait tourner ça tout seul et SONNE au bandeau en cas de
  changement (caméra tombée = alerte critique). C'est de la présence d'ÉQUIPEMENT réseau (« quelle caméra
  répond »), jamais d'identité de personne.
- VUE SYNOPTIQUE PAR SECTEUR + SEUIL D'ATTAQUE COORDONNÉE : en tête des sites distants, une rangée de
  pastilles donne la santé de chaque secteur d'un coup d'œil — « Secteur Est : 4/5 en ligne » — VERTE si
  tout répond, AMBRE si une caméra manque, ROUGE si on atteint le seuil. Ce SEUIL (réglable, « alerte
  secteur si ≥ N caméras tombent ») déclenche, quand plusieurs caméras d'un même secteur lâchent SUR LE
  MÊME CYCLE de re-scan, une alerte CRITIQUE « attaque coordonnée possible » (brouillage, coupure de
  liaison, sabotage simultané) avec « vérifier le secteur / envoyer une patrouille ». Toujours de la
  présence d'équipement réseau, jamais d'identité.
- JOURNAL (MAIN COURANTE) + EXPORT PDF DU PÉRIMÈTRE : chaque site tient un JOURNAL horodaté de ses
  changements (« + caméra apparue », « − caméra tombée »), consultable d'un clic (« Journal ») — une
  vraie main courante pour la relève. Et « Export PDF périmètre » génère, côté navigateur (aucun envoi
  externe), un PDF d'une page : pour chaque site, les caméras EN LIGNE à l'instant T et les tombées
  récentes — transmissible à la hiérarchie / une autorité. Des adresses d'équipement réseau, pas des
  personnes : jamais d'identité.
- ZONES PAR POLYGONE — PLUSIEURS PAR SOURCE (n'armer que le périmètre) : « Définir / Ajouter une zone »
  laisse tracer un polygone (clics sur l'image) ; on peut en poser PLUSIEURS par caméra (ex. le portail
  ET le dépôt), chacune retirable (« Zone 1 ✕ »). Seul ce qui bouge DANS L'UNE des zones compte — la
  route au bord, un arbre qui remue, un passage public hors emprise sont ignorés. Les zones sont
  mémorisées par source (data/drones.json), affichées en surcouche, et s'effacent d'un clic. Moins de
  fausses alertes, l'attention sur VOS secteurs.
- ARMEMENT DE NUIT — GLOBAL OU PAR EMPLACEMENT : une case « N'alerter que sur une fenêtre horaire »
  (ex. de 19 h à 6 h, minuit traversé géré) restreint les ALERTES à cette plage pour TOUTES les sources.
  Et chaque caméra peut avoir SA PROPRE fenêtre (« Fenêtre nuit propre à cette source ») qui l'emporte
  sur le global — un portail armé 20 h→5 h, un dépôt sensible armé 24/24, une zone de passage de jour
  laissée tranquille : des RÈGLES PAR EMPLACEMENT. Hors fenêtre, le poste continue de suivre et de
  journaliser, mais SANS faire sonner le bandeau — on ne réveille la garde que quand c'est anormal.
- EXPORT PDF DU DOSSIER DE PREUVE : « Export PDF » génère, côté navigateur (aucun envoi externe), un PDF
  d'une page : la capture pleine résolution + l'horodatage, la source, le site, l'état de mouvement et
  le descriptif des pistes (cap, vitesse, immobile/croisement). Le PDF joint aussi l'ÉTAT DU PÉRIMÈTRE
  RÉSEAU au même instant (caméras en ligne / tombées par secteur) — utile en enquête (ex. une caméra du
  secteur tombée juste avant la présence captée). C'est une pièce transmissible à une autorité ou à la
  hiérarchie. Elle décrit CE QUI A ÉTÉ VU (mouvement, gabarit, heure), pas QUI — l'œil humain qui recevra
  le PDF fait l'identification, comme pour une photo de vidéosurveillance.
- CE QU'ON NE FAIT PAS : AfriControl SUIT et ANALYSE ; il ne PILOTE pas le drone, ne lui commande rien,
  n'est pas une arme. Il dit « ça a bougé là, ça va vers la droite, plutôt tel gabarit » — jamais
  « c'est untel ». PAS de reconnaissance de VISAGE, PAS de lecture de PLAQUE, PAS de ciblage :
  l'identité reste à l'œil humain sur la capture. Le proxy n'accepte qu'une URL déjà inscrite au
  registre (pas un proxy ouvert), et seulement une image ou un flux d'images.
- LIMITES ASSUMÉES : le marquage ami sur la carte suppose que le drone ÉMET l'ADS-B avec un hex/
  indicatif qui matche (un drone muet reste au registre et à l'analyse d'image, sans piste air) ; la
  veille/suivi suppose une URL d'image ou de flux jointe — sinon le drone est juste suivi/inscrit ;
  l'indice piéton/véhicule est une aide, pas une certitude — l'œil tranche. La détection reste fondée
  sur le MOUVEMENT (fond médiane multi-trames), pas sur un détecteur d'objets entraîné — mais avec les
  parades ci-dessus : présence immobile TENUE indéfiniment (plus de fonte), occlusion traversée par
  prédiction + apparence (les id se récupèrent au croisement) et signalée, éclairage neutralisé,
  bruit/éclair rejeté par la médiane. Résidu honnête restant, minime : deux cibles de MÊME apparence
  (même clair/sombre, même taille) qui se recouvrent exactement peuvent encore permuter — on le
  signale. Pour le lever complètement, un FLUX vidéo continu (MJPEG en place ; RTSP via passerelle) et,
  le jour venu, un détecteur embarqué sur VOS caméras — AfriControl reste côté réception/analyse, sans
  identité.

Comparateur avant/après — Capteurs > onglet « Changement »
- Pas de direct : un satellite ne repasse que tous les quelques jours. On ne traque pas une voiture
  qui roule ; on compare deux PASSAGES DATÉS du même périmètre. C'est pour ça qu'on lance des
  satellites : chaque passage est une date, et le changement se lit ENTRE deux dates.
- Choisir un site minier, « Analyser le périmètre » : le poste va chercher deux composites
  Sentinel-2 10 m du même cadre — un récent (20 derniers jours) et un ancien (fenêtre finissant il y
  a ~45 j). Un curseur (swipe) montre l'avant et l'après ; le bouton « Afficher le changement »
  allume en orange ce qui a bougé (une piste neuve, un bâtiment, un engin apparu) et donne un % de
  changement estimé.
- Honnêteté : c'est une DIFFÉRENCE D'IMAGE, pas une détection d'objet ni une identification. À 10 m
  on lit une piste ou un carreau, jamais une voiture isolée ni un visage (comme Google montre la
  scène mais floute les plaques). Réception / lecture seule : le poste lit Copernicus, il ne commande
  aucun satellite. Nécessite la clé Copernicus gratuite (même clé que la couche « Sentinel-2 ») ;
  sans clé, l'onglet le dit au lieu d'inventer une image.

Sites surveillés — ajouter ses propres sites au périmètre de sécurité (Capteurs > Changement)
- Le lot d'usine (sites miniers) n'est jamais complet. L'opérateur ajoute ses propres sites — camp,
  poste avancé, forage, village, pont — avec un champ : Nom, Latitude, Longitude, Rayon (km).
- Chaque site ajouté compte comme un site intégré :
  · une CRUE / un SÉISME / un VOLCAN à moins de 200 km SONNE (impact régional) ;
  · un FEU à moins de 40 km SONNE (serré, pour ne pas sonner sur chaque feu de brousse du Sahel à
    150 km mais alerter dès qu'un foyer touche le périmètre) ;
  · le périmètre est armé et évalué contre l'intrusion drone, comme une bulle de protection ;
  · le site devient sélectionnable dans le comparateur avant/après.
  L'alerte porte « près de <site> (<km>) », et le badge « site surveillé » apparaît dans le volet
  Phénomènes mondiaux.
- RECHERCHE DE LIEU intégrée : en Afrique les cartes publiques décrochent après Abéché (Ennedi, BET,
  Ouaddaï, Wadi Fira… Amdjarass n'est sur presque aucune carte). Un champ « Rechercher un lieu »
  contient un répertoire Tchad/Sahel (Amdjarass, Fada, Faya, Abéché, Biltine, Iriba, Guéréda, Am
  Timan, Mao, Bongor, Doba, Ounianga, Zouar, Gouro… + sous-préfectures) : tape le nom, le poste
  remplit les coordonnées — sans dépendre d'une carte externe mauvaise ou hors-ligne. Tolère les
  accents et la casse (« amdjarass » = « Amdjarass »). Ces lieux affinent aussi le « lieu le plus
  proche » des phénomènes dans tout le théâtre tchadien.
  COUVERTURE ÉTENDUE au-delà du Tchad : le DARFOUR voisin (El Fasher, Nyala, Geneina + l'intérieur :
  Zalingei, Ed Daein, Kutum, Kabkabiya, Mellit, Tawila, Gereida, Buram, Kas, Um Dukhun, Mukjar, Kornoi
  et la frontière de Tiné) — essentiel pour un poste à N'Djamena qui regarde par-dessus la frontière —
  et les trous du SAHARA/SAHEL (Ténéré nigérien : Dirkou, Séguédine, Madama ; Adrar des Ifoghas malien :
  Ménaka, Tessalit, en plus de Gao, Tombouctou, Kidal, Agadez, Faya, Kufra, Khartoum déjà présents).
- STOCKAGE PARTAGÉ : les sites sont enregistrés SUR LE POSTE (serveur, fichier data/watch-sites.json),
  donc partagés par tous les navigateurs qui parlent à ce poste et conservés au redémarrage — plus
  seulement dans un seul navigateur. Un miroir local sert à peindre instantanément au chargement.
  Jusqu'à 1000 sites. Réception seule : on surveille, on n'émet rien. (Pour partager entre PLUSIEURS
  postes physiques distincts, il faudrait un serveur central commun — à câbler si besoin.)

Navigation directe jusqu'au site (Capteurs > Navigation)
- En zone saharo-sahélienne (BET, Ennedi) il n'y a pas de route : on tient un CAP, pas un itinéraire
  routier (comme en mer, comme au désert). Le poste calcule, d'un point à un site :
  · le CAP VRAI (° + rose des vents) et une flèche boussole ;
  · la DISTANCE grand-cercle (orthodromie) et l'ETA à la vitesse de marche choisie.
- Départ : bouton « Position GPS » (si une antenne GPS est branchée), un lieu du répertoire, un site
  surveillé, ou des coordonnées. Destination : idem. Cap vrai — ajouter la déclinaison magnétique si
  on suit une boussole.
- ÉTAPES : on enchaîne des points de passage (« Ajouter une étape ») pour contourner une zone connue ;
  distance, caps et ETA sont cumulés sur toute la route.
- CARTE DE ROUTE : un schéma trace l'axe, les étapes et les obstacles (pastilles) ; il se met à jour
  en continu.
- CAP MAGNÉTIQUE : le poste affiche aussi le cap magnétique (= cap vrai − déclinaison). La déclinaison
  est pré-estimée pour le Sahel (approchée, ±2°, à vérifier sur carte) et reste éditable.
- SÛRETÉ DE L'AXE, EN CONTINU : à chaque relevé, le poste balaie la route et signale les obstacles
  CAPTÉS (crue, feu, séisme) à moins de 25 km, avec « à X km sur la route · Y km à gauche/droite ».
  Si l'axe n'est pas sûr :
  · il PROPOSE UN CONTOURNEMENT (point de passage décalé qui dégage les deux demi-étapes) — un clic
    « Insérer le contournement » l'ajoute comme étape et l'axe repasse « dégagé » ;
  · s'il ne trouve aucune route sûre (≤ 180 km de détour), il conseille le DEMI-TOUR et propose
    l'itinéraire retour. C'est le « faute de route sûre, on rebrousse » demandé.
- SUR LA CARTE DU COP : la route (axe), les étapes et les obstacles s'affichent aussi sur la vraie
  carte imagerie du poste (onglet Situation), pas seulement dans un schéma — on les voit sur le relief
  et les villes du répertoire.
- ALARME / NOTIFICATION : quand un NOUVEL obstacle réel surgit à moins de 25 km de la route ACTIVE,
  le poste pousse une alerte dans le bandeau ET sonne (bip court), même si on n'est pas sur l'onglet
  Navigation. Interrupteur « Alarme sonore ». Un même foyer ne re-sonne pas à chaque relevé.
- PROFIL DE TERRAIN : bouton « Profil de terrain » → le poste interroge un service d'élévation public
  (ASTER GDEM 30 m, opentopodata) et trace l'altitude le long de la route (min–max, dénivelé D+) pour
  repérer un massif à franchir. ~30 m : un relief se voit, pas un ravin d'un mètre. Nécessite Internet.
- ITINÉRAIRE ROUTIER (OSM) : bouton « Itinéraire routier » → là où des routes existent (axes
  principaux, ex. N'Djamena–Abéché), le poste trace la route réelle (OSRM/OpenStreetMap) avec distance
  et durée ; la route tracée sur le COP suit alors les pistes. En zone sans route (BET, Ennedi) OSM
  accroche une route lointaine : c'est détecté (trajet aberrant) et le poste revient au CAP DIRECT. On
  a donc les DEUX : itinéraire routier quand il existe, cap direct sinon.
- EXPORT GPX / POINTS : « Export GPX » télécharge la route (et les obstacles en waypoints) au format
  GPX 1.1 — importable par un GPS de véhicule (Garmin…) ou une appli carto. « Copier les points »
  copie les « lat, lon » en texte, à dicter à la radio ou coller dans un GPS basique.
- ROUTES MÉMORISÉES (partagées) : « Enregistrer cette route » garde une route validée sur le poste
  (serveur, data/routes.json), partagée par tous les navigateurs et conservée au redémarrage. « Charger »
  la rouvre. Comme les sites surveillés.
- ALARME DE FRANCHISSEMENT : champs « Pente max % » et « Alt. max m » (limites du véhicule). Sur le
  profil, le poste affiche « franchissable » ou « FRANCHISSEMENT » avec la pente moyenne max et le
  sommet. La pente est une MOYENNE entre relevés (~30 m) : un massif se voit, pas un mur local.
- IMPORT DE POINTS (zones non sourcées) : le répertoire ne couvre pas tout. On colle une liste —
  une ligne par point « Nom, lat, lon » ou « lat, lon » — et on en fait une ROUTE ou des SITES
  surveillés, sans carte externe. Ainsi un lieu absent du répertoire (relevé GPS, point connu) entre
  quand même.
- INSPECTION IMAGERIE DE L'AXE : sous la route, une liste de points (nommés d'après le répertoire)
  avec un bouton « Capture » → ouvre l'imagerie réelle de ce point, à inspecter À L'ŒIL. L'image
  n'est PAS analysée par la machine (pas de détection auto) — on la regarde, segment par segment.
- ZOOM RELIEF : le profil global lisse les pentes. « Zoom relief » ré-échantillonne finement
  (~300 m/pas) le tronçon le plus raide pour attraper une barre qu'une moyenne masque — dans la
  limite de la résolution ~30 m (une falaise sous 30 m reste invisible).
- LIMITES ASSUMÉES : l'imagerie est un FOND, pas une source d'analyse (l'œil tranche). Le profil
  donne l'altitude et la pente moyenne, PAS la nature du sol (roche / sable) ni la franchissabilité
  réelle — ça reste la reco. En zone vierge : le cap marche toujours avec des coordonnées ; le nom
  et la route routière, non.
- Honnêteté : navigation directe par cap OU itinéraire routier OSM selon le terrain, PAS de guidage
  d'arme. Le contournement est une proposition ; le relief et les pistes se lisent sur l'imagerie et à
  l'œil. Réception seule : ça aide un véhicule à tenir un cap ou suivre une piste.

Durcissement défensif
- En-têtes de sécurité sur chaque réponse (nosniff, Referrer-Policy no-referrer, Permissions-Policy
  capteurs coupés). Aucune télémétrie tierce. Les sources externes (1090ES, météo…) sont
  interrogées PAR LE SERVEUR : l'adresse IP de l'opérateur n'est jamais exposée aux agrégateurs.
- Audit des dépendances : 0 vulnérabilité (npm audit, dépendances de production).

Liaison Internet du site (wifi opérateur / Starlink / Thuraya) — Capteurs > Outils
- Ces liens sont gérés par le SYSTÈME (Windows/Linux) : on connecte le PC au wifi, à Starlink ou au
  terminal Thuraya comme d'habitude ; AfriControl utilise le lien Internet actif, il n'en pilote aucun.
- « Liaison Internet » (en tête des Outils, bouton « Tester la liaison ») teste en direct si le poste
  atteint ses sources (imagerie, réseau 1090ES, météo) et dit EN LIGNE / PARTIEL / HORS LIGNE.
    EN LIGNE  : tout répond, l'imagerie live charge normalement.
    PARTIEL   : un domaine est bloqué par un pare-feu → autoriser les domaines listés plus bas.
    HORS LIGNE: pas d'Internet (lien coupé) → l'imagerie live ne charge pas ; le poste retombe sur la
                mosaïque locale SI les packs de tuiles sont installés (sinon carte sombre).
- Carte sombre ? 1) « Tester la liaison » : hors ligne → vérifier wifi/Starlink/Thuraya ; 2) en ligne
  mais sombre → laisser 10–20 s à l'imagerie fine pour charger (tuile par tuile) ; 3) pour l'offline,
  installer les packs de tuiles.
- Packs de tuiles hors-ligne (mosaïque locale quand il n'y a pas de ligne) : EXTRAIRE les archives
  AfriControl-2-tuiles-z8.zip et AfriControl-3-tuiles-z10-z12.zip À LA RACINE du dossier — elles
  créent public/sentinel/<z>/<x>/<y>.jpg (c'est là que le poste les lit). Fournies à part du zip de
  code pour ne pas l'alourdir. En ligne (wifi/Starlink/Thuraya), elles ne sont PAS nécessaires :
  l'imagerie fine vient du réseau ; elles ne servent que si le lien tombe.

Derrière un proxy d'entreprise
Le serveur du poste (Node) n'utilise un proxy que si on le lui dit :
  NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://proxy:port npm run dev   (Node 22.21 ou plus récent)
